Agent Oversight Explainer

Human oversight of AI agents at machine speed: see what they’re doing, ask why, and step in.

Clickable mockup · built on the team’s Agent Oversight Dashboard spec

We built on the team's Agent Oversight Dashboard spec and added one thing: the ability to ask why about anything an agent does. Everything you'll see is a clickable mockup with a sample session; the controls are simulated.

Agents work faster than people can follow

Out of sight

A helper agent does work you never see in the terminal.

Going in circles

It fixes its own fix, again and again, on one failing test.

Gone quiet

It stalls, and nobody notices for ten minutes.

Off script

It installs an unvetted library or edits code it shouldn’t touch.

Source: team spec, docs/specs/2026-11-04-agent-oversight-dashboard-design.md

These four failure modes come straight from the team's spec. By the time you spot them in a scrolling terminal, the damage is done. The goal is to catch them while you can still steer.

These are the six goals in the spec. One person, local only, Claude Code only. Agent output is always treated as data, never as instructions to the dashboard.

Ask why reads, never acts

A read-only Claude agent answers from the events and session log, with citations.

Hooks are Claude Code's built-in extension points. They send each event to a local server, which works out the plan and raises alerts. The same hooks carry steering back. Our explainer only reads, so it can't change anything the agent is doing.

One project, five zoom levels

LevelAnswers the questionWhat you see
ExecIs it on track?Plan goals, % done, plain-English updates
L1What is it doing, and why?Plan steps, helpers, short summaries
L2Which parts are changing?Folders, grouped actions, test results
L3Exactly which operations?Every tool call, file and command
L4Show me the evidenceRaw events and file diffs

Alerts show at every level. The startup interview picks your default level.

The same data at different depths. An executive sees one sentence and a red, amber or green status; an engineer drops to L3 or L4 to see the exact commands. In the mockup, keys 1 to 5 switch levels.

Spot trouble, then step in

Alerts it raises

Edit loop: same file changed 5 times in 10 min

Test-fail loop: same test fails 3 times running

Stall: a helper goes quiet for 5 min

Unvetted library: install not on the approved list

Hand-hacking: edits inside installed libraries

Off-scope: work that matches no plan step

Ways to step in

Steer: send guidance at the next tool call

Pause or Stop: one helper or the whole session

Hold: a risky command waits for Approve or Block

Kill: offered when a stalled agent can’t hear you

Detector thresholds are the spec's proposed defaults and are configurable. Every alert links to the events that triggered it, and you can acknowledge, dismiss, or stop a type of alert from showing again. Hold mode is the spec's pre-emptive option: the dashboard blocks the call until you decide.

Our addition

Ask why about anything on the screen

Cites its evidence

Every answer links to the events it used.

Speaks your level

One sentence at Exec; tool calls and diffs at L3.

Admits gaps

Says “not in the session log” instead of guessing.

“Why did it update the Linear ticket?”

Not in the session log. You didn’t ask for it, and the agent didn’t say why. Evidence: #1, #2, #27.

This is what the spec doesn't have yet. Click any box, event or alert and ask why it's there or what it does. The key design rule: the explainer only uses what the agent actually did or said, and when there's no reason in the log it says so. In the mockup the answers are hand-written samples; in the build a read-only Claude agent writes them.
